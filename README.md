# 🩺 Clinical Research Assistant

An AI research assistant that reasons over **ClinicalTrials.gov**, **PubMed**, and an **internal trial-operations database** at once — delivering **grounded, cited** answers about clinical trials, published biomedical literature, and your own study portfolio. Built as a Life Sciences demo — enterprise-grade UX, source-grounded responses, no fabrication.

---

## Features

### Intelligence
- **Single tool-capable agent** — every message runs through a LangGraph ReAct agent with live tool access. The model decides when to call tools and when to answer from context; there is no brittle pre-classification step.
- **Three live sources, one turn** — public trial registry, biomedical literature, and your internal operations data. For combined questions the model calls multiple tools **in parallel** and keeps the sources clearly separated.
- **Grounded by design** — field values come only from tool output. Missing fields render `Not specified`; the agent never invents NCT IDs, enrollment counts, eligibility, or results, never asserts a superlative ("highest enrollment") about a value it hasn't retrieved, and never conflates internal numbers with public-registry numbers.
- **Retrieval-aware follow-ups** — "which of those has the highest enrollment?" triggers a real query rather than a guess; pure follow-ups ("summarise the first one") answer from context with no tool overhead.
- **Adaptive output** — structured trial/paper cards for research, a compact operations format for internal data, conversational prose for follow-ups and definitions.

### Research
- **Multi-source search** — ClinicalTrials.gov and PubMed via MCP (Model Context Protocol), independently or in parallel.
- **Source grounding** — NCT IDs and PMIDs are scraped directly from raw tool output, not generated by the model.
- **Structured cards** — trials (NCT ID, status, phase, enrollment, condition, sponsor, location) and papers (PMID, authors, journal, study type, key finding).
- **Inline citations** — a `📎 Sources` footer with clickable ClinicalTrials.gov / PubMed links at the bottom of each response.
- **Live tool status** — each database call surfaces as a step badge as it happens.

### Internal trial operations (natural-language → SQL)
- **Query your own portfolio in plain English** — the agent translates questions about your studies, sites, and per-site enrollment into SQL over a local database and answers in real time ("how is enrollment tracking?", "which sites are behind target?", "list our active Phase 3 oncology studies").
- **Composes with the public sources** — internal studies carry a `nct_id` that links to ClinicalTrials.gov, so the agent can compare your accrual to the competitive landscape and the latest literature in a single answer — something no public source can do alone.
- **Self-contained & safe** — one model pass turns the question into a single `SELECT` against an embedded schema with few-shot examples; read-only is enforced at two layers (SELECT-only validation **and** a read-only connection), results are row-capped, and a malformed query self-corrects once or degrades gracefully. Synthetic demo data only — no real patient information.

### UI & UX
- **Live token streaming** — responses stream token-by-token.
- **Personalised greeting** — time-of-day greeting with the signed-in user's real name (from Google profile).
- **Sound effects** — send and done cues via the Web Audio API (zero dependencies).
- **Randomised starters** — the welcome screen rotates 4 questions from a curated pool each session.
- **Branded enterprise theme** — deep-blue header, Inter typography, custom CSS/JS.

## Architecture

```
User message
     │
     ▼
LangGraph ReAct agent  (gpt-4o-mini + tools)
     │   model decides per the system prompt:
     ├── public trials/literature?   → ClinicalTrials.gov / PubMed MCP tools (parallel when both apply)
     ├── our portfolio/enrollment?    → query_trial_operations (NL → SQL, local DB)
     └── answerable in context?       → respond directly, no tool call
     │
     ▼
Stream tokens → scrape NCT/PMID sources → append inline citations → persist to Supabase
```

A single agent instance is created **once per server lifetime** (`_shared_agent` in `app.py`) — tools are fetched once, not per session, eliminating per-reload latency. All tools are bound through one shared builder (`research_agent.build_agent()`) wrapped for error-resilience and output caps. Conversation state is kept in `lc_messages` (last 6 messages) in the Chainlit user session. Synchronous Supabase writes run via `asyncio.to_thread` so they never block the event loop.

The internal database is a local SQLite file generated deterministically at boot from an embedded synthetic seed (`trial_ops.ensure_db()`) — nothing to host, nothing to commit, and no network dependency that can fail mid-demo.

The system prompt (`prompts.py`) is assembled from independently editable sections: identity, scope, follow-up handling, tool selection, compliance, **grounding/anti-fabrication**, and output format.

## Tech Stack

| Layer | Technology |
|---|---|
| LLM | OpenAI **gpt-4o-mini** (`langchain-openai`) |
| Agent framework | LangGraph `create_react_agent` (ReAct loop with tool binding) |
| Data sources | ClinicalTrials.gov MCP · PubMed MCP (third-party hosted) · internal SQLite (NL→SQL) |
| NL→SQL | Self-contained tool — embedded schema + few-shot, read-only guards (stdlib `sqlite3`, zero extra deps) |
| UI | **Chainlit 2.11** (ShadCN/Tailwind) |
| Auth | Google OAuth (beta whitelist) |
| Persistence | Supabase (Postgres) |
| Observability | LangSmith tracing + a standalone eval suite (groundedness / no-overcalling / scope) |
| Hosting | **Render** (auto-deploys on `git push`) |

## Local Setup

**Prerequisites:** Python 3.13, an OpenAI API key, a Supabase project, and Google OAuth credentials.

```bash
# 1. Clone
git clone https://github.com/metafloyd/clinical-research-agent.git
cd clinical-research-agent

# 2. Virtual environment
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # macOS / Linux

# 3. Install dependencies
pip install -r requirements.txt

# 4. Configure .env (see below)

# 5. Run
.venv\Scripts\python.exe -m chainlit run app.py --port 8504
```

### Environment variables (`.env` locally / Render dashboard)

```
OPENAI_API_KEY
DATABASE_URL
SUPABASE_URL
SUPABASE_SERVICE_KEY            # one service-role key for Postgres + Storage
SUPABASE_STORAGE_BUCKET         # bucket for persisted chart figures (e.g. "elements")
OAUTH_GOOGLE_CLIENT_ID
OAUTH_GOOGLE_CLIENT_SECRET
CHAINLIT_AUTH_SECRET
CHAINLIT_URL=https://clinical-research-agent.onrender.com
# optional: LANGSMITH_TRACING, LANGSMITH_API_KEY, LANGSMITH_PROJECT
```

> Google OAuth redirect URIs must include both the local callback
> (`http://localhost:8504/auth/oauth/google/callback`) and the production one.

> The internal trial-operations database needs no configuration — it is created
> automatically on first run.

### CLI Runner

A standalone command-line interface tests the agent directly without the Chainlit UI:

```bash
.venv\Scripts\python.exe research_agent.py
```

1. Push to GitHub (`main` auto-deploys).
2. Build: `pip install -r requirements.txt` · Start: `bash start.sh` → `chainlit run app.py --port $PORT --host 0.0.0.0`.
3. Set the environment variables above in the Render dashboard.

## Data Sources

| Source | What it covers |
|---|---|
| [ClinicalTrials.gov](https://clinicaltrials.gov) | Active, recruiting, and completed trials — phase, enrollment, eligibility, sponsor, status, results |
| [PubMed](https://pubmed.ncbi.nlm.nih.gov) | Published results, systematic reviews, meta-analyses from 35M+ articles |
| Internal trial operations | Your own study portfolio — per-site enrollment vs. target, recruitment status, PI, phase, therapeutic area (synthetic demo data, local SQLite) |

The two public sources are accessed via hosted MCP servers — no API keys required for data access. The internal source is a local database queried in natural language.
